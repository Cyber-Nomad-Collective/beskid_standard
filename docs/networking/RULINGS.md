# Networking program rulings

Decisions made without the owner present, with the basis for each. Revisit any
of them through an OpenSpec change when this work is specified.

| # | Date | Ruling | Basis |
| --- | --- | --- | --- |
| R1 | 2026-10-05 | Protocol packages live in `protocols/` and depend on an unmodified 0.5.2 corelib until a CLI grants corelib authority per service file (0.5.3). Then they move to `corelib/packages/`. | 0.5.2 grants corelib services only to a byte-identical bundle (`beskid_abi/src/corelib_bundle.rs`). |
| R2 | 2026-10-05 | Coordination inside a connection uses preallocated flag arrays, `Fiber.Join` and short polls, never one channel per connection or stream. | 0.5.2 runtime: 64 channels per process, never freed (COMPILER-GAPS C10). |
| R3 | 2026-10-05 | Happy Eyeballs: 250 ms connection attempt delay (clamped 100 ms..2 s), 50 ms resolution delay, IPv6 first, interleaved families. | RFC 8305 sections 3, 4, 5, 8. |
| R4 | 2026-10-05 | URI parsing rejects inet_aton host forms (`127.1`, `0x7f.1`, `2130706433`) and accepts only strict dotted-decimal IPv4. | RFC 3986 section 7.4 warns about rare IP address formats; WHATWG URL treats them differently, so strict rejection avoids ambiguity. |
| R5 | 2026-10-05 | AES and GHASH are table-based for now (not constant-time against cache timing); they move to hardware instructions through CLIF blocks in 0.5.3. | Performance and side-channel guidance: Bernstein 2005 cache-timing; Go/BoringSSL use AES-NI/PMULL. |
| R6 | 2026-10-05 | RSA keys in certificate validation require at least 2048 bits. | NIST SP 800-57 Part 1 Rev. 5 table 2; CA/Browser Forum Baseline Requirements 6.1.5. |
| R7 | 2026-10-05 | X.509 tolerates keyUsage BIT STRINGs with trailing zero bits and an explicit `critical FALSE`, because real roots in the macOS bundle encode them; negative serial numbers stay rejected. | RFC 5280 section 4.1.2.2 and 4.2; observed in `/etc/ssl/cert.pem`. |
| R8 | 2026-10-05 | WebSocket never offers extensions (no permessage-deflate) and caps messages at 64 KiB by default. | RFC 6455 section 9; RFC 7692 is optional; runtime array limit (W5). |
| R9 | 2026-10-05 | Messages larger than buffers are written in pieces (header, then payload through a 4 KiB scratch buffer); nothing buffers whole bodies. | Runtime traps out_of_memory near 160 KiB of live arrays (W5). |
| R10 | 2026-10-06 | AES is vector-permute AES (vpaes) and GHASH is BearSSL ghash_ctmul64, both constant time, replacing the table versions of R5; hardware AES/CLMUL waits for compiler opcodes. | Hamburg, CHES 2009; OpenSSL vpaes-x86_64.pl; BearSSL ghash_ctmul64.c; Cranelift 0.136 has no AES/CLMUL opcodes. |
| R11 | 2026-10-06 | Poly1305 uses radix 2^64 with 128-bit products (OpenSSL poly1305.c) instead of donna 5x26. | RFC 8439 2.5; 64x64 products available through `umulhi`. |
| R12 | 2026-10-06 | 256-bit fields (X25519, P-256, ECDSA mod n) use generic 4x64 Montgomery CIOS with masked final subtraction; X25519 keeps the RFC 7748 ladder with masked swaps. | Koc-Acar-Kaliski 1996; RFC 7748 5; Renes-Costello-Batina 2016 complete formulas unchanged. |
| R13 | 2026-10-06 | To reach native-class AES-GCM/SHA throughput, 0.5.3 lets a clif block pass array payload pointers to C-ABI `[Extern]` calls (no GC safepoint is reachable in foreign C code; the GC is non-moving), and crypto gains an optional native acceleration provider (OpenSSL libcrypto EVP on Linux, CommonCrypto on macOS) behind the unchanged API, with the pure-Beskid CLIF code as reference and fallback. JIT/AOT also get an optimizing Cranelift level. | Cranelift 0.136 has no AES-NI/CLMUL/SHA opcodes; rustls `CryptoProvider` design (provider abstraction with a pure fallback); owner ruling that pure Beskid is not a hard requirement. |
| R14 | 2026-10-06 | The Web client sends one request per connection (`connection: close` on HTTP/1.1, GOAWAY on HTTP/2) and has no connection pool yet; the server serves connections one after another on the calling fiber, and callers spawn `ServeTlsConnection`/`ServePlainConnection` per stream for concurrency. | 0.5.2 runtime limits (64 channels per process, contract values not storable in structs) make a shared pool keyed by origin a separate design; correctness first. |
| R15 | 2026-10-06 | Over TLS the client and server accept an empty ALPN result as HTTP/1.1 only when "http/1.1" was offered; any protocol not offered fails with `WebError::AlpnMismatch`. HTTP/1.0 and close-delimited responses stay rejected (corelib Http codec). | RFC 7301 section 3.2 (no ALPN = application default); RFC 9113 section 3.2; RFC 9112 section 6.3. |
| R17 | 2026-10-06 | HTTP/3 reaches QUIC only through `Http3.H3Quic.QuicLink`, an enum of concrete transports (`Memory`, `Quic`); a `Quic` link carries the QUIC stream ids, FIN, RESET_STREAM codes and application CONNECTION_CLOSE codes unchanged. A close below HTTP/3 (QUIC transport error, idle timeout) reports `CloseCode` = H3_INTERNAL_ERROR and `TransportFailed` = true, and the client API surfaces it as `H3Error::Transport`. | RFC 9114 sections 3, 6, 8; contract values cannot be struct fields in 0.5.2 (codec gap). |
| R18 | 2026-10-06 | `H3Client.ConnectQuic` offers only ALPN "h3" and fails closed (closes with H3_VERSION_FALLBACK, returns Transport) if any other protocol is negotiated; `ListenQuic` accepts only "h3". Each side grants the peer 3 unidirectional and 8 bidirectional streams. Addresses are IP literals; name resolution stays with the caller (or the later `Web` facade). | RFC 9114 sections 3.1, 6.2 (three unidirectional streams per side); HQ1 import collision. |
| R19 | 2026-10-06 | The HTTP/3 writer sends DATA frames of at most 4 KiB, and `H3Quic.Close` waits up to 1 s for written stream data to be acknowledged before CONNECTION_CLOSE so a final GOAWAY is delivered. | Runtime large-array limit (HQ3); RFC 9000 section 10.2 (no stream data in the closing state); RFC 9114 section 5.2. |
| R20 | 2026-10-06 | The native acceleration provider of R13 is the opt-in package `packages/crypto-openssl` (`corelib_crypto_openssl`, modules `CryptoOpenSsl.*`). It depends on `corelib_crypto` and holds every libcrypto import. It exposes drop-ins with the core signatures: `NativeSha256.Hash`, `NativeSha512.Hash512`/`Hash384`, `NativeHmac.Compute`/`Digest`, `NativeAesGcm` (own key type `NativeAesGcmKey`) and `NativeChaCha20Poly1305` `Seal`/`Open`/`SealInto`/`OpenInto`. `Provider.SelfTest()` is a known-answer check against the pure kernels. `Provider.Select()` returns `Pure` when `BESKID_CRYPTO_PROVIDER=pure` is set or the self-test fails, else `Native`; callers call it once and keep the result. Linux only (OpenSSL 3 `libcrypto.so.3`: one-shot `SHA256`/`SHA384`/`SHA512`/`HMAC`, EVP AEAD with a context created and freed per call). The native `OpenInto` zeroes the output range on a tag failure (EVP decrypts before it verifies) and returns `AuthenticationFailed`. Inputs of 2^30 bytes or more, and streaming hash/HMAC states, use the pure kernels. `corelib_crypto` stays pure and references no native symbol. macOS (CommonCrypto) and public-key algorithms through EVP_PKEY come later. TLS/QUIC select the provider in process only after the compiler supports runtime-optional externs (COMPILER-GAPS NATIVE1). | rustls provider crates (`rustls::crypto::CryptoProvider`; ring and aws-lc-rs chosen at build time); 0.5.3 resolves every referenced extern at load time and CLIF blocks admit no `call_indirect` (repro `crypto-openssl/repros/missing-extern-library`); OpenSSL 3 EVP_EncryptInit_ex(3) and EVP_CIPHER_CTX_ctrl AEAD controls. |
| R21 | 2026-10-06 | With compiler 0.5.3 the protocol packages move from `protocols/` to `packages/` and join the corelib aggregate (the opt-in `crypto-openssl` package of R20 moves too but is not registered in the aggregate). A package depends on `corelib_foundation` plus exact sibling packages (never the aggregate, to avoid a cycle); test and interop projects depend on the aggregate only. Program docs move to `docs/networking/`. Repros keep the 0.5.2 pristine corelib for baseline comparison. | 0.5.3 grants corelib authority per canonical service file (R1 condition met). |
| R22 | 2026-10-06 | `Http3Mode::Prefer` (https only) tries HTTP/3 first and falls back to TLS over TCP only while no QUIC connection has negotiated "h3" (resolution, handshake, ALPN, or budget failure). After that, an error is returned and the request is not retried over TCP, because the server may already have processed it. `Http3Mode::Only` never uses TCP and fails with `WebError::Http3Failed`. The QUIC handshake budget is `http3HandshakeMillis`, 1 s by default. | RFC 9114 section 3.1 (a client may try HTTP/3 and use another version when it fails); RFC 9110 section 9.2.2 (only idempotent requests are retried automatically); the 1 s budget keeps a TCP-only origin at about one extra second. |
| R23 | 2026-10-06 | The Web HTTP/3 client connects to IP literals directly and resolves names with `Network.Dns` (both families, resolver order). It tries the addresses one after another, giving each an equal share of the remaining handshake budget. It does not race them. Trust is the TCP path's policy (`config.trust` or the system bundle), with ALPN "h3" only. | RFC 8305 section 8 (sequential fallback is allowed); 0.5.2 runtime: an endpoint plus a driver fiber per attempt, and a 64-channel limit (R2). |
| R24 | 2026-10-06 | `WebError::Http3Failed(code)` carries `H3Errors.CodeOf` of the H3Error (RFC 9114 / RFC 9204 code). Timeout and Transport have no wire code, so they map to `WebErrors.Http3TimeoutCode()` = -1 and `Http3TransportCode()` = -2 (`Web.WebH3.CodeOf`). | The variant stays `i64`, as the reserved API declared. Negative values cannot collide with wire codes. |
| R25 | 2026-10-06 | `Web.ServeQuic` serves connections one after another on the calling fiber (as in R14). Each connection is served until the client closes it, it is idle for `idleTimeoutMillis`, or `maxRequestsPerConnection` is reached. An open connection ends with GOAWAY and then CONNECTION_CLOSE H3_NO_ERROR. HTTP/3 bodies use the Http3 default limit of 64 KiB, not the 128 KiB limit for HTTP/1.1 and HTTP/2. | RFC 9114 section 5.2; runtime large-array limit (HQ3). |
| R26 | 2026-10-06 | QUIC stream error codes (local and peer RESET_STREAM and STOP_SENDING) are -1 until a frame is sent or received. This is because 0 is a valid application code (H3 codes start at 0x100, but other applications can use 0). `QuicConfig.WithStreamLimits` is the only way to change peer stream limits. HTTP/3 sets 8 bidirectional and 3 unidirectional streams through it. | RFC 9000 sections 19.4, 19.5, 4.6; RFC 9114 section 6.2. |
