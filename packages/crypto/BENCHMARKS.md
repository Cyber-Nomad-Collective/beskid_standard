## Native provider (`packages/crypto-openssl`, ruling R20)

`beskid test --project packages/crypto-openssl/tests --target NativeBench` (0.5.3 CLI, JIT at
`opt_level=speed`, one run, load about 2.7). Each row runs the pure and the native drop-in
in the same test. Inputs are one-shot 16 KiB buffers: 1 MiB per pure run, 8 MiB per native
run. OpenSSL HW is the `openssl speed` reference from the table above.

| --- | --- | --- | --- |

| AES-128-GCM seal + open, 16 KiB | n/a | 3748 MB/s | n/a |

The remaining gap to `openssl speed` is per-call overhead. Each AEAD call creates, keys, and
frees an `EVP_CIPHER_CTX` (about 2 us per 16 KiB record), and each HMAC call runs `HMAC()`
from the start, including the key pads. A reusable keyed context needs a handle that is
freed on every path, which Beskid 0.5.3 cannot guarantee without finalizers. Streaming
SHA/HMAC states and inputs of 2^30 bytes or more still use the pure kernels.

## What runs in CLIF

All kernels are generated by `tools/clifgen.py` (AES from the checked model in
`tools/vpaes.py`); regenerate with `python3 tools/clifgen.py`.

- SHA-256/512: full compression, schedule interleaved with the rounds, loop over blocks in
  one function.
- ChaCha20: four blocks in i32x4 lanes (rotations by byte shuffle and shift/or), keystream
  XOR over the payload; single-block kernel for tails and QUIC header protection.
- Poly1305: radix 2^64 with `imul`/`umulhi` (OpenSSL `poly1305.c` structure).
- AES: constant-time vpaes (Hamburg 2009, OpenSSL vpaes-x86_64) through `swizzle`, four
  CTR blocks interleaved; rounds are a Beskid loop around three blocks (one fully unrolled
  4-wide AES-256 dominated JIT time). Replaces the secret-indexed T-tables.
- GHASH: BearSSL `ghash_ctmul64` (constant time, no tables).
- 256-bit Montgomery fields (4 x 64 CIOS, branch-free): ModArith width 8, the whole X25519
  ladder loop, P-256 complete addition/doubling and the fixed-window scalar multiplication
  with constant-time masked table reads.
- RSA/BigNat: 64-bit CIOS Montgomery multiplication in 4-limb chunk blocks for widths 8k.

## Remaining gap and why

- Hardware instructions: Cranelift 0.136 exposes no AES-NI, PCLMULQDQ or SHA-NI opcodes,
  so AES-GCM, GHASH and SHA-256 stay software. Against software baselines the gap is 1.6x
  (SHA-256), 1.8x (SHA-512), 2.3x (AES-GCM, OpenSSL SW also uses vpaes), 2.8x (ChaCha).
- JIT at `opt_level=none`: no GVN/LICM/egraph rewrites inside the kernels.
- Calls with array arguments cost about 70 ns each (GC root register/unregister per array
  parameter), and a Beskid store to an `i64[]` calls the write barrier. Kernels therefore
  loop inside one function and keep their cursors in payload stores, but the public-key
  code still calls one function per field or point operation outside the hot loops, and
  the RSA kernel runs one block per 4-limb chunk with its state in memory (325 us vs
  15 us). A size-specialised, fully unrolled row kernel would close most of the RSA gap.
- Allocation: `Slice.New(n)` appends byte by byte (16 us for 64 bytes); fixed buffers now
  come from literals (`Crypto.Scratch`), but each HMAC still allocates two hash states,
  which is most of the 11 us per 64-byte HMAC.
- P-256 uses generic Montgomery reduction and a 4-bit window without precomputed
  generator tables; OpenSSL/ring use a p256-specific reduction and large comb tables.
